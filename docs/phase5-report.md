# Phase 5 implementation report

Phase 5 connects student contributions to durable, aggregate current occupancy. Opening a location with no recent evidence shows **Not enough recent data**. A check-in alone does not claim a percentage; a categorical crowd report can establish a low-confidence estimate that gains confidence as independent signals agree. The map, Home, Explore, detail and recommendation screens consume the same live catalog summaries. Seed forecasts and historical examples remain clearly labeled.

## Delivered architecture

- **Models and migrations:** `CheckIn`, `CrowdReport`, `OccupancyValidation`, and extended `OccupancyEstimate` snapshots. Alembic revisions `25630308138d`, `25630308138e` and `25630308138f` create constrained, indexed tables and signal-summary fields. PostgreSQL is authoritative; raw GPS coordinates are never persisted.
- **API:** Authenticated `POST /checkins`, `GET /me/checkins/active`, `POST /checkins/{id}/checkout`, `POST /crowd-reports`, `POST /occupancy-validations`; public `GET /locations/{id}/occupancy`. Existing list, nearby and detail endpoints load current snapshots in bulk. They exclude seed estimates and show unknown when evidence is absent or too old.
- **Check-ins:** A partial unique index enforces one active visit per user. Same-location retries return the active record; switching locations completes the previous visit. Checkout is idempotent and owner-only. Visits have a configurable four-hour maximum and expired visits never count as active, even before the expiry job runs.
- **Reports and validation:** Students choose a broad crowd category and may optionally supply a foreground coordinate pair. Reports and validations are rate-limited for ten minutes per user and location; Redis provides a fast report-cooldown key, while a PostgreSQL query under a user lock enforces the same rule after a cache failure. Validation requires the current estimate ID and records one response per estimate. Mutations recompute and persist a new aggregate snapshot.
- **Estimator:** The weighted median of recent reports resists isolated outliers. Categories normalize to 20, 50, 75 and 92 as modeling assumptions. A 25-minute half-life, bounded reliability factor and proximity factor determine weights. Recent trusted manual observations strongly anchor the result. Check-ins and validations influence confidence but cannot invent a percentage without reports or a trusted observation. Snapshot confidence reflects signal volume and agreement; read-time confidence decays with a 45-minute half-life. Estimates older than 90 minutes display as unknown.
- **Reliability:** New users start at 0.5. After at least three distinct recent reporters yield medium-confidence consensus, each unassessed report can change its author's internal score by only +0.01 or -0.01, clamped to 0.2–1.0. Other users never receive contributor identities or reliability scores.
- **Redis:** `studyspot:occupancy:{location_id}` caches an aggregate snapshot for 60 seconds. `studyspot:ratelimit:report:{user_id}:{location_id}` caches cooldown state. Missing or failed Redis reads fall back to PostgreSQL; reports and check-ins remain durable. List and nearby endpoints use one bulk PostgreSQL snapshot query rather than N per-card API requests.
- **Mobile:** The existing check-in/report screen now submits to the API. Home shows the caller's active location and checkout control. Detail shows confidence, update age, limited-data/unknown states and validation buttons. Screens refresh on focus and detail/map poll while visible; no background location collection or WebSocket system was introduced.
- **Expiry:** `python -m app.jobs.expire_checkins` is a one-shot idempotent job. Schedule it every minute with an external scheduler for a deployed API. Query predicates independently ignore overdue check-ins.

## Local startup and Phase 6 handoff

From the repository root run `docker compose --env-file infrastructure/.env -f infrastructure/compose.yaml up -d db redis`. In `backend`, configure `.env`, run `uv sync`, `.venv/bin/alembic upgrade head`, `.venv/bin/python -m app.seed.run`, then `.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8001`. Schedule `.venv/bin/python -m app.jobs.expire_checkins` every minute. In `mobile`, run `npm ci` and `npm run web`, or build a native development client. Normal sign-in still requires a Supabase project; browser tests use isolated local identities.

Phase 6 can consume timestamped reports, check-ins, validations, trusted observations and estimate snapshots with signal counts. The source/reliability/proximity metadata is retained for later evaluation. No ETL, trained forecast, sensor integration, push delivery or production orchestration was added.

Physical-device GPS, native map rendering and production Supabase sign-in were not verified in this workspace. A prior iOS build compiled MapLibre but failed in Expo's generated Constants script on the spaces in the workspace path. OpenFreeMap has no uptime guarantee; operators can configure another compatible style. The expiry job must be scheduled in each deployed environment, and there is no trusted-observer admin endpoint until an admin authorization boundary exists.
